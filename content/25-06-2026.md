This blog talk about the MongoDB architecture. Then dives into CAP theorem and how MongoDB handles the trade-offs.

# MongoDB Architecture

MongoDB database system follows the following architecture from top to bottom:

- Document
- Collection
- Database
- Node
- Cluster

## Document

MongoDB document is the smallest unit of data. It contains data related to an object and its associated metadata. The object is a field-value pair where the value can be of many types - string, number, date, array, object and more.

## Collection

Multiple documents together make up a collection. In SQL language, collection is same as entity but with differences due to its polymorphic design. A collection can contain multiple forms of entity and document shapes due to the flexible schema design of MongoDB.

## Database

A database contains multiple collections. When we say database, we generally mean database management system (DBMS) but here database means multiple collections together.

## Node

Node and Cluster make the MongoDB a distributed system. Node is where an individual MongoDB instance is running. A node can be a physical or virtual or a containerized machine.

## Cluster

Cluster is collection of nodes. Cluster can be of two types - replica set and sharded cluster. Replica set provides high availability to MongoDB architecture. And sharded cluster provides scalability with a method called sharding.

# CAP Theorem & MongoDB

CAP theorem explains that availability, consistency and partition tolerance cannot be achieved simultaneously in a distributed system.

Consistency: Multiple nodes will respond with the same data or error.
Availability: Every read/write request should give a response even if it is not consistent.
Partition Tolerance: If there is a network problem between nodes, the system should still function properly.

MongoDB achieves partition tolerance through sharding cluster and replica set. Now it is up to user how they want to balance between consistency and availability. MongoDB replica set provides high availability. And read/write concerns help achieve consistency.

Replica set is multiple mongod instances managing the same dataset. mongod is the daemon process that processes requests, manages data and provides response.

Sharding is the mechanism MongoDB use to scale. Sharding will shard/partition the data in MongoDB into multiple different nodes. Each shard is a subset of the sharded data, and together it makes up a single logical database for a sharded cluster. It provides MongoDB horizontal scalability. By adding more shards, one can distribute the data and ensure database performance remains well. But, it requires careful planning and add complexity.

Read concern decides the consistency and isolation level of the data while reading from the replica set or sharding cluster. The default value is "local". It means the read operation will return result from the same node where the request is received. It ensures high availability and low latency. But it may be inconsistent. It can be changed to another setting like majority.

Write concern dictates the number of replica set members that must confirm a write operation. The default value is "majority". It means that majority of the replica set members will acknowledge that the operation is successful. It results in consistent write operations.

# Conclusion

To summarize, MongoDB ensures high availability through replica sets. It achieves consistency with read/write concerns and finally it provides scalability with sharding.
