Today I learnt about the architecture of Prometheus from this [link](devopscube.com/prometheus-architecture/). Here, I will summarize what I have learnt.

The architecture of Prometheus includes -

1. Prometheus server
2. Time-series Database (TSDB)
3. Targets
4. Exporters
5. Service Discovery
6. Push Gateway
7. PromQL
8. Alert Manager

# Prometheus Server

Prometheus server is the brain of the monitoring system. It pulls metrics data from the targets in scrap intervals. Scrap interval can be set in the configuration file.

Metrics are numerical measures to understand the state of any service. Targets are simply the endpoints, pods or services. Scraping is the term used in Prometheus to refer to pulling metric data.

# Time-Series Database

The metric data change with time. So, Prometheus need a time-series database to handle such data properly.

Prometheus stores the data in local storage in the format of chunks. It compacts old data to save space and provides retention policy to clean up old data.

Prometheus provides 2 ways of retention policy - time based and size based.

Time based retention policy will keep the data for specified time duration and then remove it. Size based policy will remove the old data if data size exceeds the specified size.

# Targets

Target is the source of metric data. Prometheus scraps the target for metric data. By default, the path for collecting metric from target is `/metrics`.

But, the endpoint for scraping metrics could be customized through the configuration file.

Prometheus expects the metric data in a certain text format.

# Exporters

Exporters are like agents that are running on the target to convert the metric data generated in that system to format that Prometheus accepts.

By default, these converted metrics are exposed by the exporter on `/metrics` endpoint.

# Service Discovery

Prometheus provides 2 ways for scraping the metric from target.

Static configs: When the target has a static IP or DNS endpoints, that endpoint can be used as the target.

Service Discovery: In most autoscaling and distributed systems like Kubernetes, the target will not have static endpoint. In that case, target endpoints are discovered through Prometheus service discovery and targets are added automatically to the configuration.

Prometheus server asks the service discovery method to discover the target and then automatically adds the correct address based on the search.

# Push Gateway

Normally Prometheus pulls metric data from targets. But there are some situations where the source of metric data is temporary e.g. batch jobs. In such cases, Prometheus provides a solution called Push Gateway. Push Gateway is kind of an intermediate gateway which runs as a standalone component. The batch jobs can push the metrics to Push Gateway. Push Gateway exposes the metrics on `/metrics` endpoint. Then, Prometheus scraps the metrics from push gateway.

# PromQL

PromQL is a flexible query language to query time-series data from Prometheus.

We can directly query in the UI platform of Prometheus or use curl to make a query over the command line.

The data can also become a source to tools like Grafana where PromQL can be used to query data and create dashboards.

# Alert Manager

Alert manager is one important component of Prometheus. It sends alerts based on metric threshold. The threshold is set in the configuration file.

The alert gets triggered by Prometheus and sent to notification system/receivers (email, slack etc.) configured in the configuration file.
